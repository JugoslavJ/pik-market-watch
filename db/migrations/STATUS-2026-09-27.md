## Phase 5 dependency audit (2026-09-28)

The validation window has not passed yet. The runtime cutover's first full
lean scrape finished at 09:12:11 UTC; the 12-hour scheduler has not completed
its next full cycle. No Phase 6 SQL has been run.

The final-cleanup audit found public objects that the earlier draft of the
Phase 6 instructions did not account for:

* The raw-response archive currently holds 2,286 compacted response rows,
  7,374 shared JSON documents, and 9,390 JSON fragments (about 18 MiB for
  the response-record table alone). `raw_api_response_pending` is empty.
* `raw_api_response_records` and `raw_api_response_pending` have foreign keys
  to `public.listings` and `public.scrape_runs`. The lean scraper continues
  using this archive for payload retention and maintenance, so those archive
  tables must move to `lean` and their FKs must target lean listings/runs
  before the public source tables can be removed. Keep the archive and its
  logical read/maintenance behavior.
* `public.scrape_run_pages` has 2,669 rows and is useful request evidence; it
  can be retained in `lean`.
* `detail_jobs` contains 1,688 rows, all with `status='succeeded'`; there are
  no pending or claimed requests to recover. Lean uses per-listing retry
  timestamps instead.
* The old monthly tables are inheritance children, not declarative
  partitions. The current catalog has 314 inherited child relations across
  `public` and `olap` (74 each for daily facts, market daily, listing daily,
  and price events; 13 state-history children; 5 price-history children).
  Drop children explicitly before parents during Phase 6.

The migration plan now records these dependencies and corrects its fresh-
install baseline step. `db/init/*.sql` is checksum managed by
`schema_migrations`; already-applied files must not be overwritten. A lean-
only baseline and matching migrator contract need to be tested on a disposable
fresh volume before the old baseline is retired. Phase 6 cleanup remains
blocked by the stated 3–5 day validation gate, not by unresolved user
decisions.

The additive archive migration is now prepared as
`07-lean-raw-archive.sql`. It copies the decoded rows from the public logical
archive view into `lean.raw_api_responses`, retains `scrape_run_pages`, checks
IDs and full row contents, and targets lean listing/run FKs. Lean capture,
retention, and replay code now target this table and no longer call the
legacy JSON compaction functions after the archive table exists. Before that,
the staged code detects the absent lean table and safely falls back to the
public archive with lean IDs kept in request metadata. The migration is
intentionally not applied yet; deploy that code only after the migration has
run during Phase 6. It stores decoded JSONB directly, so the old
document-fragment layout is removed while raw payload history itself remains.

The fresh-install baseline is also prepared in `db/init-lean/`; it keeps all
already-applied `db/init/` files untouched. It includes PostGIS, six lean
domain tables, the operational raw archive and page-history tables, all 56
neighborhood boundaries, and the lean-compatible role bootstrap. Compose can
select it with `DB_INIT_DIR=./db/init-lean` after the validation gate. The
migrator now recognizes the full lean schema contract and can adopt either a
freshly initialized lean database or the completed live conversion. A
database-backed fresh-install test was added. Unit tests pass, but the focused
database test was skipped because `TEST_DATABASE_URL` is unset; the disposable
Docker run is currently blocked by access to the Docker engine named pipe.
